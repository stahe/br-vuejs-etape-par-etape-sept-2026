    7. O servidor RdvMedecins, uma caixa-preta

    Os exemplos 17 a 20, seguidos do estudo de caso, interagem com um servidor: o servidor JSON da aplicação [RdvMedecins]. Este é o servidor [NestJS] do curso anterior, cujos controllers deixam de gerar páginas HTML e passam a produzir respostas JSON. Suas camadas de negócio e de acesso a dados permanecem inalteradas.

    Neste curso, esse servidor é uma caixa-preta: não precisamos saber como ele é escrito. Importa apenas sua API — isto é, a lista de requisições HTTP que ele aceita e as respostas que retorna. Essa é a situação típica de quem desenvolve um cliente: a API é um contrato, e a equipe do servidor pode mudar o que quiser por trás desse contrato. O código-fonte dele é fornecido (pasta [rdvmedecins-nestjs-json]) e amplamente comentado, para o leitor curioso.

    Este capítulo explica como instalar o servidor, descreve sua API e o consulta usando o [curl].

    7.1. A aplicação RdvMedecins

    A aplicação gerencia as consultas de um consultório médico. Ela tem três papéis:

    Papel
    Quem
    O que pode fazer
    [ADMIN]
    O administrador ([admin])
    Agendar e cancelar consultas de todos os pacientes; gerenciar médicos e clientes
    [DOCTOR]
    Os médicos ([pelissier], [tatou], [dupont])
    Agendar e cancelar consultas de todos os pacientes; ver todos os nomes nas agendas
    [USER]
    Os pacientes ([martin], [durand], [bistrou], [german])
    agendar consultas para si mesmos; cancelar suas consultas; gerenciar suas contas. Em uma agenda, não podem ver os nomes dos outros pacientes

    As contas de demonstração usam o login como senha. As regras de gestão são verificadas pelo servidor, independentemente do cliente:

    • nenhuma consulta no passado;
    • apenas uma consulta futura por paciente;
    • um horário só pode ser reservado uma vez por dia;
    • dois médicos (ou dois clientes) não podem ter o mesmo nome e sobrenome; um login pertence a uma única conta;
    • um médico com consultas não pode ser excluído;
    • um registro que tenha sido modificado nesse meio tempo por outra pessoa não pode ser sobrescrito (bloqueio otimista);
    • um paciente nunca recebe o nome de outro paciente.

    7.3. Formato das respostas

    Todas as URLs começam por [/api]. Uma requisição bem-sucedida recebe um código de status 2xx e, em seu corpo, os dados solicitados no formato JSON. Uma requisição rejeitada recebe um código de status 4xx ou 5xx e, no corpo, dados no mesmo formato:

    1
2
3
4
5
6
    {
  "statusCode": 400,
  "key": "ERRORS.INVALID_FORM",
  "params": { "min": "6" },
  "fields": { "lastName": "ERRORS.LASTNAME_REQUIRED", "password": "ERRORS.PASSWORD_TOO_SHORT" }
}
    • [statusCode]: o código HTTP, repetido no corpo;
    • [key]: a chave de tradução da mensagem. O servidor nunca retorna texto a ser exibido: ele não conhece mais o idioma do usuário. É o cliente que traduz a chave usando seus dicionários (veja o Exemplo 16);
    • [params] (opcional): os parâmetros da mensagem ([At least {min} characters.], [Try again in {minutes} minute(s).]);
    • [fields] (opcional): para um formulário rejeitado, o erro de cada campo.

    7.4. Autenticação

    O cliente se autentica por meio de [POST /api/auth/login], com um nome de usuário, uma senha e uma resposta ao CAPTCHA. Em troca, o servidor coloca no navegador um cookie que contém um token JWT assinado:

    1
    Set-Cookie: rdvmedecins_jwt=eyJhbGciOiJIUzI1NiIs...; Max-Age=7200; Path=/api; HttpOnly; SameSite=Strict

    Seus atributos são importantes para a segurança:

    • [HttpOnly]: o código [JavaScript] da página não consegue ler esse cookie. Um script malicioso injetado na página seria, portanto, incapaz de roubar o token. Consequência para o cliente: ele não consegue determinar por conta própria se está logado. Ele pergunta ao servidor ([GET /api/auth/me]);
    • [Path=/api]: o navegador só o inclui nas requisições à API;
    • [SameSite=Strict]: o navegador só inclui esse token nas requisições enviadas A PARTIR de uma página deste site. Uma página maliciosa em outro site não consegue fazer o navegador agir em nome do usuário (um chamado ataque CSRF);
    • [Max-Age=7200]: ele expira após duas horas, ao mesmo tempo que o token.

    O navegador envia então automaticamente esse cookie a cada requisição a [/api]. O cliente [Vue.js] não tem, portanto, nada a fazer para se autenticar, desde que suas páginas e a API compartilhem a mesma origem (mesmo protocolo, mesma máquina, mesma porta). Esse é o papel do proxy do [Vite] durante o desenvolvimento (veja o Exemplo 17) e do próprio servidor em produção (veja o capítulo “Implantação”).

    Uma segunda salvaguarda contra ataques CSRF: o servidor rejeita (415) qualquer requisição POST cujo corpo não esteja em JSON. Um formulário HTML comprometido em outro site não consegue enviar JSON.

    1

    O servidor DECIDE; o cliente exibe. E mesmo que um cliente trapaceasse (exibindo um botão “Reservar” quando não deveria), o servidor verificaria tudo novamente no momento da reserva.

    7.6. Consultando a API com curl

    A pasta [curl] do servidor contém os corpos de requisição JSON deste capítulo, um arquivo por requisição. Por exemplo, [curl/login-admin.json]:

    1
    { "login": "admin", "password": "admin", "captchaId": "-", "captcha": "test" }

    Os comandos são digitados em um console aberto no diretório [rdvmedecins-nestjs-json]. Algumas opções do [curl]:

    • [-i]: exibir também os cabeçalhos da resposta; [-s]: sem barra de progresso;
    • [--json @file]: enviar o conteúdo do arquivo em POST, com o cabeçalho [Content-Type: application/json] (curl 7.82 e posteriores; com uma versão mais antiga, use [-H "Content-Type: application/json" -d @file]);
    • [-X PUT], [-X DELETE]: o método HTTP;
    • [-c cookies.txt]: salvar os cookies recebidos neste arquivo; [-b cookies.txt]: enviá-los de volta. É assim que o [curl] “permanece logado” de um comando para o seguinte, exatamente como faria um navegador.

    No [PowerShell], é preciso digitar [curl.exe], e não [curl] (que designa outro comando). As respostas um tanto longas em JSON foram formatadas para este documento, e os cabeçalhos [Date], [ETag], [Connection], e [Keep-Alive] foram removidos.
